## Cross-cutting decisions (locked)

1. **Offline-only.** No runtime network I/O. Sole exception: `#if DEBUG` model bootstrap (LAN fetch). Enforced by convention + a Core guard that throws on `HttpClient` use outside the bootstrap class.
2. **Engine seams.** `IStoryEngine` (outline/scene/polish/poster-spec calls), `ITtsEngine` (sentences → PCM + timestamps), `IPosterComposer`. `TemplateStoryEngine` + platform-TTS are permanent fallbacks; `LlamaStoryEngine` + `SherpaTtsEngine` are the real path, selected at startup by `IModelProvider.Availability`.
3. **LLM**: llama.cpp pinned tag, vendored headers, one `LlamaNative.cs` (~25 fns, blittable marshalling). iOS `llama.xcframework` (`DllImport("__Internal")`, Metal); Android `libllama.so` arm64-v8a (`DllImport("llama")`, CPU 4 threads). Model: Qwen3-1.7B-Instruct Q4_K_M (SHA256-pinned), mmap'd; context 8k; `/no_think`. All JSON stages decoded under GBNF grammars from Contracts.
4. **TTS**: sherpa-onnx C API. Android via NuGet `org.k2fsa.sherpa.onnx` runtime; iOS via sherpa xcframework + own P/Invoke. Kokoro-82M int8, speakers af_bella/af_sarah/am_michael = Ember/Willow/Sage, speed 0.92. Output: per-sentence PCM → WAV → m4a (platform encoder) + `NarrationManifest` timestamps. Teaser = first ~3 sentences rendered first.
5. **Posters**: `PosterSpec` is enum-constrained (12 curated palettes; shapes moon, stars, hills, water, cloud, pine, fox_silhouette, lighthouse, boat, window_glow; exactly 4 depth layers). Composer is deterministic (same spec → same pixels; seeded scatter). Each layer rasterized ONCE at 1.15× viewport; parallax = `TranslationX/Y` on prerendered images from low-pass-filtered `OrientationSensor` (α=0.08, travel ±4/9/15/24 px by depth). Flattened 512px PNG thumbnail per story.
6. **Pipeline**: stages Outline → Scenes·stitch·polish → Poster → Narration; progress weights 5/40/5/50 recalibrated from device history; checkpoint after every (stage, scene, window, sentence) to SQLite; local notification on completion. Cooldown 30 min (premium 15) via monotonic-anchored persisted timestamp.
   **Hosting (background-weave pass 2026-07-31).** `WeaveHostService` owns the pipeline Task; staying alive outside the foreground is delegated to `IWeaveBackgroundAnchor` (Core abstraction, one implementation per platform, called on every start and on every exit path).
   - **Android — real background execution.** `Platforms/Android/WeaveForegroundService` is started when a weave begins and stopped on completion / failure / cancel. Type `specialUse` with a manifest `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` justification: `shortService` caps at ~3 min (weaves run 3–15) and ANRs if blown, `dataSync` is transfer-shaped and carries a 6 h/24 h budget with an `onTimeout`→ANR contract on Android 15+, `mediaProcessing` covers only the narration stage under the same budget. The service holds a PARTIAL wake lock (`taleweaver:weave`, 45-min ceiling) — a foreground service keeps the *process*, only the wake lock keeps the *CPU* once the screen sleeps — and posts a silent LOW-importance "The loom" notification (`WeaveNotificationCopy`, ≤1 update / 10 s) that taps through to MainActivity.
   - **iOS — honest maximum, in three layers.** (1) While the loom hum is audibly playing on the `Playback`/`SpokenAudio` session with `UIBackgroundModes: audio`, the app keeps running and the weave simply continues. (2) If the hum is off, `WeaveBackgroundCoordinator` takes a `BeginBackgroundTask` assertion on backgrounding, logs the granted budget rather than assuming it, and on expiry cancels-with-checkpoint (never `CancelAndDiscardAsync`). (3) It also submits a `BGProcessingTaskRequest` (`net.frostaura.taleweaver.weave-resume`, `RequiresExternalPower=false`) whose handler resumes through `TryResumeAsync` — opportunistic, promised in no copy.
   The half-woven story and its checkpoint always survive a background suspend; resume-on-launch is unchanged and remains the floor under all of the above.
   **Scheduling strategies (perf pass 2026-07-31).** The pipeline picks one of two schedules per weave and stamps it into the checkpoint (a resume always continues the schedule it started under; pre-strategy checkpoints resume sequentially):
   - **Overlapped (default on ≥ 6 GB devices)** — producer–consumer. The LLM producer polishes per ~2-scene *window* as scenes complete (`IStoryEngine.PolishWindowAsync`; only the final window may write the goodnight close) and hands polished windows to a channel; the TTS consumer narrates windows in order while later scenes still generate. Teaser = first ~3 sentences of window 1, rendered FIRST, exactly as before. After the final window's LLM work the **poster runs off the critical path**, in parallel with the remaining narration (poster needs the LLM, narration needs sherpa — no contention). Each window renders to `story-{id}-part{w}.wav` (no tail silence except the last window; windows ≥ 2 carry a fixed paragraph beat as leading silence); at completion the parts are PCM-concatenated into `story-{id}.wav` and part files deleted. **Sentence indices/timestamps stay globally exact**: windows join FullText with a blank line, the sentence splitter treats paragraph blocks independently, so split(FullText) ≡ concat(per-window splits); window-local timestamps are appended with cumulative index/time offsets. Per-window peak normalization replaces whole-story normalization (same voice, same target — inaudible difference; measured). **Progress under overlap** is combined completion: percent = weighted sum of all four stage fractions under the same 5/40/5/50 weights (monotone — every term only grows); the reported `WeaveStage` is the furthest stage *started* (monotone), so the weave sheet's row derivation stays sensible and the Narration row reads "weaving…" the moment its first window starts. **Memory**: LLM (Qwen3 Q4 ~1.2 GB mmap) + Kokoro fp32 (~0.4 GB) are co-resident BY DESIGN — acceptable on ≥ 6 GB devices (8 GB-class phones), which supersedes §11's dispose-before-TTS rule *for this strategy only*. Overlap is picked only on devices with ≥ 6 GB RAM **and ≥ 6 cores** (see fallback below).
   - **Sequential (constrained-device fallback + forced)** — the classic order (all scenes → whole-story polish → poster → narration), LLM never co-resident with active TTS. Picked automatically when `IDeviceCapabilities` reports a low-RAM device, &lt; 6 GB physical memory, **or &lt; 6 logical cores** — llama and sherpa each run min(4, cores) threads, and on a 4-core device the co-resident stages thrash each other (measured on the 4-vCPU emulator: overlapped 16.6 min vs sequential+KV 10.7 min for the same story). Core's default signal reads `/proc/meminfo` on Android/Linux (the Mono GC signal under-reports there) and the GC signal elsewhere; platform heads may pre-register richer signals (Android `ActivityManager.lowRam`). Forcible via `TaleWeaverOptions.ForcedWeaveStrategy` (harness `weave --strategy sequential`). Kept fully tested — it is also the resume path for legacy checkpoints.
   **KV prefix cache (same pass).** `LlamaRunner` keeps the llama context's KV memory alive across a weave: each call tokenizes its prompt, finds the longest common token prefix with what the previous call left resident (prompt + generated tokens), removes only the divergent tail via `llama_memory_seq_rm(mem, 0, lcp, -1)` (pinned tag b10189) and decodes just the suffix. Sampling quality is untouched (sampler chain is fresh per call and only ever accepts generated tokens); a model-gated test proves cached-vs-fresh output identity. Full clear remains the fallback (`ReuseKvPrefix=false` or non-removable memory). Measured on the Mac harness: the shared system prompt + per-stage preambles come from cache, cutting most prompt re-ingestion.
7. **Safety**: age-banded prompts (3–4/5–6/7–8) → GBNF/enum construction → lexicon filter per scene → ≤2 LLM self-repair passes → scene regeneration. Kid free-text never enters a prompt. Story Bible writes pass the same filter.
8. **Persistence**: sqlite-net-pcl, single `taleweaver.db3` in AppData. Audio + poster PNGs on disk, DB stores paths. Storage screen sums real bytes.
9. **Entitlements**: local stub (`IEntitlements`): trial-nights counter from first-run date, premium flags all false; UPGRADE → coming-soon sheet. Client-trust pattern reserved for M4.
10. **Analytics**: NONE. Removed entirely by founder decision 2026-07-31 — no toggle, no settings member, no sink, no event names. There was never an ingest endpoint; now there is no seam either, and a reflection test keeps it that way.
10b. **Audio session & native players (2026-07-31).** One shared session, three tenants, one owner of the system surface.
   - **Session (iOS):** category `Playback` with `AllowAirPlay | AllowBluetoothA2DP`, mode `SpokenAudio`, activated on narration load and by the loom hum through the *same* configurator (`Platforms/iOS/NativeAudio.ConfigureSession`) so no tenant can leave it in a shape that degrades AirPlay. `PlayAndRecord` is forbidden — it routes to the earpiece.
   - **Narration owns the system surface.** `MediaElementNarrationPlayer` sets `MetadataTitle`/`MetadataArtist` (narrator persona)/`MetadataArtworkUrl` (plain path to the story's poster PNG) — on Android that populates the toolkit's ExoPlayer `MediaSession`, which is what Bluetooth, Android Auto and Cast read. On iOS the toolkit's Now Playing coverage is partial, so the app additionally writes `MPNowPlayingInfoCenter` (title, narrator, artwork, duration, elapsed, rate — elapsed+rate on every play/pause/seek so external scrubbers track) and registers `MPRemoteCommandCenter` play/pause/toggle/stop/seek/±15 s skip against the same player. Next/previous are disabled: there is no next story.
   - **The beds never own it.** The loom hum and the Premium ambient bed play through `AVAudioPlayer` / Android `MediaPlayer` and write no metadata, so an AirPlay receiver or lock screen always shows the STORY.
   - **Route loss pauses narration, never the weave.** iOS `AVAudioSession` `OldDeviceUnavailable` and Android `ACTION_AUDIO_BECOMING_NOISY` both pause playback rather than switch to the phone speaker beside a sleeping child; a weave in flight is untouched and the hum keeps going.
   - **The live-TTS fallback publishes nothing** and clears any stale entry: it is an utterance engine with an estimated timeline, so a lock-screen scrubber over it would be a lie.
11. **Model assets**: Debug → AppData via LAN/adb (resolution order AppData → bundle); Release → iOS MauiAsset bundle path via NSBundle (no copy), Android install-time pack (TTS) + fast-follow (LLM) with copy-once to FilesDir for mmap + 2 GB free-space preflight. iOS entitlement `com.apple.developer.kernel.increased-memory-limit`. LLM context disposed before TTS starts (memory ceiling discipline) **on the sequential strategy only — the overlapped strategy (§6) keeps them co-resident by design on ≥ 6 GB devices and falls back to sequential below that.**
12. **Shell map**: onboarding (3 pushed pages, first-run only) → `//home`; `player` presented modally; flat push routes `shelf`, `settings`, `library` — no route name collides with a tab/root name. QA env-var `TALEWEAVER_QA_ROUTE` cold-starts any route.
